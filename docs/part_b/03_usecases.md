## A. 진단·요청 — 결정론 · LLM 0

### 시나리오 U1 — 해피패스: 약점 데이터 충분한 학생의 세트 생성

**상황.** 재원 3개월 학생, 확정 태그 이벤트 200건. 강사가 Step 1~2에서 약점 확인 후 language×concept 10문항 요청.

1. 백엔드가 alias 스냅숏과 함께 `POST /problem-sets`(202, 멱등키).
2. 진단이 약점 지도 산출 — `weak` 셀·`root_candidate` 노드에 근거 셀 참조 동반, 목표 동결(`weakness_map_id`).
3. 문항별 생성→게이트 ①②③→체크포인트 커밋. 전 문항 통과 시 세트 `generated`.
4. Kafka `problem_set.completed` → Step 3 화면에 검증 라벨 표시.
5. 강사 선별·승인 ✋ 전까지 학생 노출 0.

**검증하는 것:** 동일 스냅숏·버전 재실행 시 바이트 동일(재현성 — 이벤트 입력 순서를 섞어도 동일, event_id 정렬 집계). 근거 없는 verdict 저장 실패. 멱등키 재요청 시 중복 생성 0.

**실패 사례 — 충돌 event_id 입력:** 스냅숏에 동일 `event_id`인데 필드가 하나라도 다른 이벤트 쌍이 섞여 오면, 임의 선택하지 않고 `DiagnosisInputConflictError`로 **전체 진단 중단**(부분 데이터로 약점 결과 생성 금지 — 04 §3.2 확정). API 경계에서는 기존 `SnapshotInvalid → 400 INVALID_SCHEMA` 매핑 — 게이트 거부(200 정상 상태)가 아니라 입력 데이터 결함이다. 완전 동일 재수신은 1건으로 처리하고 정상 진행.

### 시나리오 U2 — 데이터 부족: 자동 개인화 거부 → 수동 목표 출제 (확정)

**상황.** 등원 1주차 신규 학생 — 표본이 `cell_min_items` 미달.

1. 자동 개인화 요청은 `rejected_insufficient`(200 + 정상 상태 — 에러 아님)로 종료. "데이터를 모으는 중" 안내.
2. 강사가 영역·노드를 직접 선택하면 `target_source=teacher_manual`로 재요청 — 진단 생략, 일반 출제 진행.
3. 결과 메타·화면에 **"약점 데이터 기반 개인화 아님" 필수 표기**(`weakness_map_id=null`).

**검증하는 것:** 부족 판정이 게이트에서(억지 진단 금지). manual 세트에 개인화 표기가 없으면 계약 위반. `GateRejected` 5xx 승격 금지.

### 시나리오 U3 — 기준 자료 없음: T1 사전·문법 자료 조회 불가

**상황.** T1 문항 생성 중 기준 자료(D-03) 다운 또는 버전 불일치 — R-1 대조 불가.

1. 해당 문항은 추측 생성으로 통과시키지 않는다 — `verification_unavailable`로 저장·발행 차단.
2. 연속 3문항 `[잠정]` 검증 불능이면 세트 조기 중단 → `partial_success`/`failed` + 사유.
3. 자료 복구 후 재검증 배치로 합류.

**검증하는 것:** 자료 장애 시 "그럴듯한 정답" 미발행(fail-closed). stop_reason 정직 기록.

## B. 생성·게이트 — item_attempt 총 3회 공통 예산

### 시나리오 U4 — 약점 정렬 불일치: 태그는 맞는데 내용이 다른 약점

**상황.** `lang.phoneme_change`(음운 변동) 타겟인데 생성 문항이 실제로는 표준 발음 규정 지식만 측정. R-7(메타 정합)은 통과.

1. 게이트 ②에서 verifier가 blind 풀이와 함께 정렬 판정 — `aligned=false`, `measured_skill_node_id` 상이, 사유 반환.
2. 실패 사유를 구조화 주입해 재생성(item_attempt 소모).
3. 3회 소진 시 `dropped(drop_reason 포함)` — 세트에 실패 이유 표기.
4. `aligned=true`인데 `alignment_confidence`가 경계값 미만이면 폐기가 아니라 `needs_review` 배지.

**검증하는 것:** 메타만 맞고 내용이 다른 문항이 verified로 저장되지 않음. 정렬 실패가 별도 루프가 아니라 공통 예산을 소모.

### 시나리오 U5 — 규칙 검증 실패 → 재생성 → 소진

**상황.** 선지 2·4가 정규화 후 동일 문자열(R-2).

1. 게이트 ① 실패 — `retry_context`(실패 규칙 ID·이전 stem 해시) 주입 후 재생성.
2. 동일 stem 해시 재출력은 즉시 폐기(시도 소모).
3. 총 3회(최초 1+재생성 2) 소진 시 `dropped`, `drop_reason=generation_exhausted`. 나머지 문항은 계속.

**검증하는 것:** 재생성 상한 정확히 3회. R-5(금칙)만은 재생성 우회 없이 즉시 폐기. 실패 문항이 세트를 멈추지 않음.

### 시나리오 U6 — 교차 풀이 정답 불일치

**상황.** verifier(다른 모델 패밀리)가 blind 풀이에서 선지 3을 골랐는데 생성 정답은 2.

1. "선지 3도 성립" 구조화 사유로 재생성 — ①부터 다시(②만 재시도 금지).
2. verifier가 "복수 정답 가능" 표명 시에도 동일 처리.

**검증하는 것:** blind 페이로드에 answer·rationale·evidence 부재(스냅숏 회귀). verifier reasoning이 강사 해설로 노출 안 됨.

### 시나리오 U7 — LLM·검증 모델 장애 (복원력)

**상황.** verifier 벤더 429/timeout 연속.

1. gateway 전송 재시도 1회 → 소진 시 해당 문항 `verification_unavailable` — 저장은 하되 발행 차단.
2. **강사 일반 승인·지시로 우회 불가(수동 예외 승인 불허 — 확정).** 완화 수단은 verifier 폴백 패밀리(gateway 라우팅).
3. 벤더 복구 후 재검증 배치가 ②부터 재실행 — 성공 시 ③으로 합류.
4. generator 장애면 item_attempt 내 재시도 → 세트 `partial_success`/`failed` + 재시도 가능 여부 반환.

**검증하는 것:** 검증 불능 ≠ 통과(fail-closed). 장애 중 생성분이 승인 대상 목록에 안 오름.

### 시나리오 U8 — 부분 성공과 조기 중단

**상황.** 지문이 해당 유형 출제에 부적합해 10문항 중 4번째까지 dropped 3건 — 비율 30% `[잠정]` 초과.

1. 남은 생성 중단(`stop_reason=drop_ratio_exceeded`) → `partial_success` + 성공·실패 수와 사유 집계.
2. 성공 0건이면 `failed` + 원인·재시도 가능 여부.
3. 세트 실행이 비동기 총 상한에 접근하면 시간 사유로 동일 처리.
4. 프론트는 실패 문항을 숨기지 않고 성공·실패 수를 함께 표시.

**검증하는 것:** 조용한 수량 미달 금지. 조기 중단 후 완료분 보존·체크포인트 재개 가능.

## C. Step 3 — 수정·선별 (refine MVP)

### 시나리오 U9 — 핑퐁 수정 해피패스

**상황.** "3번 선지가 너무 티 나. 자연스럽게 바꿔줘."

1. 지시문 redaction·정책 정적 검사 통과 → 해당 문항+지시만 LLM 전달(세트 전체 컨텍스트 미전달).
2. 수정안 구조화 출력 → **게이트 ①②③ 전체 재실행**(부분 수정도 기존 검증 결과 재사용 금지).
3. 새 리비전 저장(diff·검증 결과·redaction된 지시문) → 라벨 갱신. 재검증 완료 전 승인 버튼 비활성.

**검증하는 것:** 매 턴 전체 재검증. 리비전·diff 저장. 수정 중 약점 목표·태그 불변(목표 변경은 Step 1~2로 회귀).

### 시나리오 U10 — 게이트를 이기려는 지시 차단

**상황.** "정답을 두 개로 만들어줘" / "근거 없이 그럴듯하게" / "학생 실명 넣어줘".

1. 실명·정책 위반은 **사전 정적 검사에서 차단 — LLM 미호출**, 차단 사유·대안 반환.
2. 정적 검사를 통과한 교묘한 지시도 산출물이 게이트 ①②에서 차단 — 문항은 마지막 검증본 유지.

**검증하는 것:** 차단 턴에 LLM 호출 0. 차단 이력도 리비전 행으로 남음(공격 코퍼스 재료).

### 시나리오 U11 — 교체·삭제·롤백

**상황.** 수정으로 살리기 어려운 문항.

1. **교체:** 같은 출제 조건으로 새 문항 생성(새 생성 계보·전체 검증) — 수정과 달리 리비전 이력이 이어지지 않음.
2. **삭제:** 세트에서 제외 — 생성 호출 0, 이력은 감사용 보존.
3. **롤백:** `revert_to=n` — 저장된 리비전 스냅숏 복원(LLM 호출 0, 복원본의 검증 결과도 함께 복원).

**검증하는 것:** 교체=새 item_id·새 예산, 롤백=호출 0. 삭제 문항의 이력 보존.

### 시나리오 U12 — 강사 직접 수정 (확정: 허용 + 전체 재검증)

**상황.** 강사가 AI 없이 발문 텍스트를 직접 고쳐 저장.

1. `revision_kind=teacher_direct` 리비전 생성(LLM 호출 0).
2. 저장 시 **게이트 ①②③ 전체 재검증** — 직접 수정이 정답 유일성·근거를 깰 수 있으므로 예외 없음.
3. 재검증 실패 시 직접 수정본은 리비전으로 남되 **이전 검증본이 현재본 유지** + 실패 사유 표시.

**검증하는 것:** 직접 수정도 재검증 필수(도메인 원칙). 실패 시 미검증본이 현재본이 되지 않음.

### 시나리오 U13 — 동시 수정 충돌 (확정: 낙관적 잠금)

**상황.** 같은 문항에 두 세션이 동시에 refine 요청.

1. 요청에 `base_revision_no` 필수 — 최신 리비전과 다르면 **409 반환**(멱등 재생 409와 구분되는 충돌 코드 — 09 §2-2 제안), 최신본 재로드 후 재시도.
2. 문항당 진행 중 refine 1건만 — 진행 중이면 후속 요청 즉시 거부.

**검증하는 것:** last-write-wins 미발생. 409 후 재시도 경로 정상.

## D. 경계·안전

### 시나리오 U14 — 승인 전 노출 차단 + 수동 예외 불허 (경계 원칙)

**상황.** ① 강사가 `verification_unavailable` 문항을 "내가 확인했으니 발행"이라 요청 ② 학생 홈이 미승인 문항 조회 시도.

1. ①: 코드 게이트가 거부 — 재검증 성공 전 어떤 승인 경로로도 발행 불가(확정). 안내: "재검증 후 발행 가능".
2. ②: suggested/verified/needs_review 전 상태가 강사 승인 전 학생 노출 0 — 노출 상태는 백엔드 소유이므로 AI는 발행 가능 플래그 자체를 반환하지 않음.

**검증하는 것:** 검증 불능 우회 경로 부재(구조적). AI 응답에 학생 노출 관련 필드 없음.
