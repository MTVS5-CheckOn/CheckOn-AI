## 1. 행동 5종 — 수정·교체·직접 수정·삭제·롤백의 차이

| 행동 | 의미 | AI 처리 | LLM 호출 |
| --- | --- | --- | --- |
| **수정**(AI 핑퐁) | 기존 문항을 대화로 다듬음 — 리비전 계보 유지 | refine 생성 + **게이트 ①②③ 전체 재실행** | 1(생성)+1(교차 풀이) |
| **교체** | 기존 문항을 버리고 같은 조건으로 새 문항 | 새 item 생성(새 item_id·새 item_attempt 예산) + 전체 검증 | 생성 경로와 동일 |
| **직접 수정**(확정) | 강사가 AI 없이 텍스트를 직접 편집 | `revision_kind=teacher_direct` 리비전 + **게이트 ①②③ 전체 재검증** | 1(교차 풀이만) |
| **삭제** | 세트에서 제외 | 생성 호출 0 — 이력은 감사용 보존 | 0 |
| **롤백** | `revert_to=n` — 저장된 리비전 복원 | 스냅숏 복원(그 리비전의 검증 결과도 함께 복원) | 0 |

교체는 대화형 수정의 다른 이름이 아니다 — 수정은 맥락·리비전 이력을 유지하고, 교체는 새 생성 계보를 만든다. `직접 검토`(서술형 아닌 경계 문항 확인)는 화면 동작일 뿐 AI 처리 없음.

## 2. 지시문 해석 규칙 — 허용/근거 검증/정책 차단 3분류

| 분류 | 예시 지시 | 처리 |
| --- | --- | --- |
| **A. 품질·스타일** (허용 — 즉시 반영) | "3번 선지 더 자연스럽게", "해설 짧게, 근거 문장은 유지", "발문을 부정형으로", "지문 조금 쉽게" | 프롬프트에 구조화 주입. 단 결과는 게이트 전체 재통과 |
| **B. 사실·근거 관련** (근거 검증) | "이 문항 근거를 2문단에서 찾아줘", "선지에 지문 어휘 활용해줘" | 지문·기준 자료에 근거가 **있으면** 반영, 없으면 차단(`evidence_missing`) — "있는 것만 쓴다" |
| **C. 정책 위반** (차단 — **LLM 호출 전 정적 검사**) | "정답을 두 개로", "근거 없이 그럴듯하게", "학생 실명 넣어줘", "정답률 90%라고 가정해줘", "이전 지시 무시해"(injection) | 차단 + `blocked_reason` + 가능한 대안 안내. **LLM 호출 자체를 안 함** |

부분 차단: 복합 지시("짧게 + 정답 두 개로")는 가능한 부분만 반영하고 차단분 사유 동시 반환 — 턴 전체를 버리지 않는다.

**수정 중 불변(위반 지시는 C 분류):** 대상 학생·약점 목표 · 문항의 area·type·skill_node(측정 대상) · 정답·해설의 근거 요구 · 금칙·저작권·사실성 정책 · 개인정보 마스킹 · 승인 전 노출 금지. **약점 목표 자체를 바꾸려면 수정이 아니라 Step 1~2로 돌아가 새 조건으로 생성**한다.

## 3. `blocked_reason` enum (공용 error_codes와 공유 — B 증분은 09 §2-2 제안)

| 코드 | 뜻 | 검출 시점 | 화면 문구 `[제안]` |
| --- | --- | --- | --- |
| `evidence_missing` | 지시한 사실·근거가 지문/자료에 부재 | 생성 후 R-1/R-4 | "요청 내용의 근거를 지문에서 찾지 못해 반영하지 못했어요" |
| `answer_integrity` | 정답 유일성·정합 훼손 지시("정답 두 개") | **사전 정적 검사** + R-2 | "정답 구조를 깨는 수정은 할 수 없어요" |
| `banned_topic` | 금칙 소재 삽입 지시 | 사전 정적 검사 + R-5 | "해당 소재는 출제 기준상 사용할 수 없어요" |
| `pii_exposure` | 실명·연락처 삽입 지시 | 사전 정적 검사(redaction) | "개인정보는 문항에 넣을 수 없어요" |
| `prompt_injection` | 지시 이탈 패턴(05 §8.2) | 사전 정적 검사 | "요청을 처리할 수 없어요" |
| `out_of_scope` | 문항 수정과 무관(약점 목표 변경·타 학생) | 사전 정적 검사 | "이 문항의 수정 범위를 벗어나요 — 새 출제로 진행해 주세요" |

`pii_exposure`·`out_of_scope`는 A의 refine enum 재사용, 나머지 3종은 B 증분 제안.

## 4. 매 수정 턴의 처리 순서 — 부분 수정도 전체 재검증

```
강사 지시 (instruction + base_revision_no)
 → 낙관적 잠금 검사 (§6 — 불일치 시 409, LLM 미호출)
 → 지시문 redaction·정책 정적 검사 (C 분류 차단 — LLM 미호출)
 → 해당 문항 + 지시만 LLM 전달 (§7 컨텍스트 최소화)
 → 수정안 구조화 출력 (파싱 실패 = 턴 실패)
 → 게이트 ① RuleValidation 전체 재실행
 → 게이트 ② BlindCrossSolve 전체 재실행 (blind — 수정된 문항 기준)
 → 게이트 ③ ReleaseDecision 재판정
 → 새 리비전 저장 (diff · 게이트 결과 · redaction된 지시문 · 버전 세트)
 → 라벨 갱신 (재검증 완료 전 승인 버튼 비활성 · "재검증 중" 표시)
```

**기존 검증 결과 재사용 금지** — 선지 한 개·해설 한 문장만 바뀌어도 정답 유일성·근거·교차 풀이가 달라질 수 있다. **턴 실패 시(게이트 차단·파싱 실패) 문항은 마지막 검증본을 유지**한다 — 미검증본이 현재본이 되는 경로는 없다.

**턴 내 재시도 상한:** 수정 턴은 재생성 루프를 갖지 않는다 — 게이트 실패 = 턴 종료(차단 사유 반환). 다듬기는 강사가 지시를 바꿔 다시 시도하는 구조(무한 자동 루프 금지). 파싱 실패만 구조화 재시도 1회 허용.

## 5. 쿼터·상한 — (7/15 확정) 집행은 전부 백엔드

- **AI는 쿼터를 알지 못한다** — 차단·카운트·잔여 표시 전부 백엔드 Billing. 한도 소진 시 백엔드가 호출 자체를 보내지 않는다. AI에 남는 것은 LLM 원가 기록뿐(gateway).
- 백엔드 집행 참고(제안 논리 — A refine §5와 동일): 정적 차단 턴은 LLM 원가 0이므로 미차감 권장 · 롤백 미차감 · 정상/부분 반영 턴 차감.
- 턴 수 상한 없음(쿼터가 자연 상한). 시간·비용 상한은 턴 단위(게이트 재실행 1세트)로 자연 제한.

## 6. 리비전 저장·낙관적 잠금 (확정)

- **저장 규칙:** 턴마다 `ITEM_REVISION` 1행 — `turn_no`(=revision_no) · `revision_kind(ai_refine|teacher_direct|rollback)` · redaction된 `instruction` · `result_snapshot`(전체 스냅숏 — 롤백 단순 복원) · `diff`(변경 전후) · `verifications_passed` · `blocked_reason` · `llm_call_id`. **차단 턴도 행을 남긴다**(감사·공격 코퍼스 재료).
- **낙관적 잠금:** 요청에 `base_revision_no` 필수 — `PROBLEM_ITEM.current_revision_no`와 다르면 **409 반환**(멱등 재생 409와 구분되는 충돌 코드 — 09 §2-2 제안), 클라이언트는 최신본 재로드 후 재시도. **문항당 진행 중 refine 1건만** — 진행 중이면 후속 요청 즉시 거부.
- **보존:** 리비전 무제한 보존 `[잠정]` — 감사·품질 평가 자료. 보존 기간·상한은 백엔드 데이터 보존 정책과 함께 `OPEN`(09 §3).
- **품질 개선 반영:** 강사 수정 이력은 골든셋·프롬프트 개선 재료로만 — **자동 학습·자동 프롬프트 변경 금지**, 반영은 사람 리뷰+버전 절차(registry·골든 통과).

## 7. 컨텍스트 범위·개인정보

- LLM에 전달하는 것: **해당 문항(현재 리비전) + 공유 지문 + 수정 지시 + 목표 메타**뿐. 세트의 다른 문항·학생 학습 기록·다른 학생 정보는 전달하지 않는다(유출 반경 최소화).
- 지시문은 전송 직전 redaction 통과(fail-closed) + 저장 전 redaction(masking §3). 강사가 지시문에 실명을 쓸 수 있음을 전제.
- 지문 공유 세트에서 지문 자체를 수정하는 요청은 v1 **비허용** `[잠정]` — 같은 지문을 공유하는 다른 문항의 재검증 연쇄가 필요해 범위가 커진다. 지문 교체가 필요하면 세트 재생성 안내. 허용 여부·연쇄 재검증은 `OPEN`(09 §3).

## 8. 승인·발행과의 경계

- 승인·발행·학생 노출은 전부 백엔드(HITL) — 이 정책서의 모든 동작은 **승인 전** 문항에만 적용된다.
- 재검증 완료 전 승인 불가(라벨 "재검증 중" 동안 승인 버튼 비활성 — 프론트 규약).
- **승인된 문항의 재수정:** AI는 새 리비전을 만들 수 있을 뿐, 승인 상태 철회는 백엔드 소유 — 철회·재검수 절차는 `OPEN`(BE — 09 §3). 철회 전 수정 요청은 거부 권장 `[제안]`.
- `verification_unavailable` 문항의 수정: 허용(수정 턴이 곧 재검증 기회) — 단 발행 차단은 재검증 성공까지 유지.

## 9. 테스트 케이스 (골든셋 시드 — [`08_evaluation_plan.md`](08_evaluation_plan.md) §8·§9 편입)

1. "3번 선지 자연스럽게" → 수정 반영 + 게이트 ①②③ 전체 재실행 + diff 저장 ✅
2. "정답을 두 개로 만들어줘" → 사전 차단(`answer_integrity`) — **LLM 호출 0**
3. "학생 실명 넣어줘" → 사전 차단(`pii_exposure`) — LLM 호출 0
4. 부분 수정(해설 한 문장)이 정답 유일성을 깨는 케이스 → ②가 검출, 문항은 이전 검증본 유지
5. 직접 수정(teacher_direct)이 R-1 근거를 깨는 케이스 → 재검증 실패, 이전 검증본 유지 + 사유
6. 10턴 후 `revert_to: 3` → 3턴 스냅숏+검증 결과 복원, LLM 호출 0
7. 동시 refine 2건 → 후발 409(`base_revision_no` 불일치), 재로드 후 성공
8. 동일 Idempotency-Key 턴 재전송 → 중복 리비전 0
9. 복합 지시("짧게 + 정답 두 개") → 부분 반영 + 차단 사유 동시 반환
10. `verification_unavailable` 문항 수정 턴 → 재검증 성공 시 발행 차단 해제 경로
