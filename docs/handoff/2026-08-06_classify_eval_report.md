### 이 표에서 읽히는 것 — **관측이지 결정이 아니다**

- **모델이 confidence를 높게만 쏜다.** 80건 중 **0.9 이상이 topic 73 · sentiment 79 · urgency 67**
  이다. 0.7 미만 구간은 **전 축 표본 0**이다 — 낮은 confidence 자체가 거의 안 나온다.
  ⇒ **임계값을 낮게 잡으면 아무것도 안 걸러지고, 높게 잡으면 대부분이 걸린다.** 분해능이 낮다.
- **urgency 0.8~0.9 구간이 50%**(10건 중 5)다. 표본 10건이라 경계선이지만, **높은 confidence에서
  정확도가 떨어지는 유일한 구간**이라 눈에 띈다.
- 🔴 **단조성이 없다.** urgency는 0.7~0.8(100%) > 0.8~0.9(50%) < 0.9~1.0(92.5%)로 뒤집힌다.
  캘리브레이션이 잘 된 모델이면 confidence가 오를수록 정확도도 올라야 한다. **표본이 얇아
  단정할 수 없지만, "임계값 하나로 자동 강등"이라는 설계 전제 자체를 재검토할 재료다.**

⚠ **표본 80건은 합성 코퍼스다.** 실사용자 데이터가 아니다.

## 6. 🔴 토큰 분포 — **이번 회차에 못 쟀다**

ⓧ(상담 경로 토큰 상한)의 값을 정하려면 이 모델의 출력 토큰 분포가 필요한데 **확보하지 못했다.**

**원인:** `classify_eval`이 **실행 원장을 적재하지 않는다.** 라우터를 거치지 않고 `classify()`를
직접 부르므로 `run_store.record_run()`이 호출되지 않는다 — 게이트웨이 기본 recorder가 수집은
하지만 프로세스가 끝나며 버려진다.

```console
$ grep -n "run_store\|record_run\|default_llm_call_collector" src/ai/evaluation/classify_eval.py
→ 0건
```

**가진 것은 단일 관측 1건뿐이다**(C-3 프로브 · 추정 아님):

| 항목 | 값 |
| --- | --- |
| `prompt_tokens` | 439 |
| `completion_tokens` | **40** |
| 지연 | 2,577ms |

### reasoning 토큰 — **분리돼 있고 값은 0이었다**

벤더 usage 스키마를 1회 확인했다:

```text
completion_tokens_details: {'reasoning_tokens': 0, 'accepted_prediction_tokens': 0,
                            'audio_tokens': 0, 'rejected_prediction_tokens': 0}
```

🔴 **두 가지 사실이 나온다.**

1. **벤더는 `reasoning_tokens`를 준다.** 그런데 **어댑터가 버린다** — `TokenUsage`는
   `tokens_in`/`tokens_out`뿐이라 `completion_tokens_details`가 기록되지 않는다(99 ⓩ 신설).
2. **이 프로브에서 `reasoning_tokens`는 0이었다.** 1차 리포트와 ⓧ가 세운 가설
   ("reasoning 토큰이 예산을 삼켜 빈 응답") **의 전제가 흔들린다.**
   ⚠ 프롬프트 1건의 관측이므로 **가설을 기각하지 않는다** — 상담 프롬프트(더 길고 복잡)에서
   0이 아닐 수 있다. **가설의 참·거짓은 아직 모른다.**

⇒ **ⓧ 값을 이 리포트에서 제안하지 않는다.** 분포가 없다.
