## 1. 🔴 R4 포함 경계가 float 오차로 배제됐다 (수정함)

### 반례 — 실제 계산값

```
정답률  baseline 80/100 · week 75/100
        diff_pp = 5.000000000000004      > 5.0  →  「초과」로 오판
시간    baseline 200/1000 · week 300/1000
        ratio   = 1.4999999999999998     < 1.5  →  「미달」로 오판
```

계약은 *"정답률 차이가 **정확히** 5.0pp면 허용"* · *"시간 배율이 **정확히** 1.5배면 발화"* 다
(`rules.py`의 조건도 `>`·`<`로 **포함 경계를 허용**하는 형태다). 도메인 입력이 정수여도
**계산 표면은 float**라 계약이 말하는 경계가 배제됐다.

### bracket으로 대체하지 않은 이유

초판은 *"5.0pp는 만들 수 없다"* 고 적고 4.6875pp/6.25pp bracket으로 우회했다. 🔴 **그건
경계 「근처」를 재는 것이고 계약이 말하는 포함 경계 자체를 재지 않는다.** 표현 불가는
`0.05`라는 **값**의 성질이지 **계약**의 성질이 아니다 — 계약을 픽스처에 맞춰 낮추면
*"구현이 계약을 지키는가"* 를 영영 묻지 않게 된다.

### 수정

`src/ai/detection/rules.py`의 R4 두 비교에 명시 허용오차를 뒀다.

```python
_FLOAT_ABS_TOL: Final = 1e-9   # 임계 간격(5.0 · 1.5)보다 훨씬 작다
```

- `threshold`를 반올림하지 않았다 · `round(v, 2)` 비교도 아니다 — 그러면 **경계가 아니라
  정밀도가 계약**이 된다.
- 설정 전체를 `Decimal`로 바꾸지 않았다(계약 표면이 넓어지고 score 계산까지 끌려온다).
- `score` 계산 방식 무변경.
- 상수를 여러 함수에 복제하지 않았다 — **반례가 나온 R4의 두 비교만** 쓴다.

### 뒤집기

| 뒤집기 | red |
| --- | --- |
| 정답률 `isclose` 제거 | 1건 (정확히 5.0pp 사례) |
| 시간 `isclose` 제거 | 1건 (정확히 1.5배 사례) |
| tolerance를 `2.0`으로 확대 | **9건** (경계 초과 사례가 통과해 버린다) |

## 2. R1에도 같은 결함이 있었다 — ✅ **#230에서 해소**

> ⚠ **아래는 A단계 감사 시점(2026-08-12 · #229)의 기록이다.** 당시에는 §4의
> *"반례가 나오면 중간 보고"* 규율에 따라 **보고만 하고 고치지 않았다.**
> ✅ **이후 #230(`fix/detect-r1-exact-threshold` · 지시서 79-R2)에서 R4와 같은 tolerance
> 정본으로 포함 경계를 복원했다.** 발견 기록은 지우지 않는다 — 지우면 다음 사람이
> *"R1은 왜 R4와 다르게 갔나"* 를 다시 판단한다(99 ㊩).

§4의 동형 감사 결과다.

| 규칙 | 포함 경계 | float 반례 |
| --- | --- | --- |
| **R1** 하락 15.0pp | 발화 | 🔴 **223건** |
| R3 기준선 40% | 미발화 | 0건 |
| R6 태깅 60% · 오답 비중 50% · 셀 정답률 50% | — | 0건 |

**엔진 실증**(정확한 하락폭이 전부 15.0pp):

```
base 18/20 → week 15/20   →  R1 발화        (float가 ≥15.0으로 떨어진다)
base 14/20 → week 11/20   →  🔴 미발화      (14.999999999999991)
base 12/20 → week  9/20   →  R1 없음(R6만)  (14.999999999999996)
base  7/20 → week  4/20   →  R1 없음(R6만)
```

§4가 *"반례가 나오면 중간 보고"* · *"R4 수정 김에 일괄 `isclose`로 바꾸지 않음"* 이라 해서
**그 회차에는 보고만 하고 손대지 않았다.**

### ✅ 해소 — **#230** (지시서 79-R2 · `fix/detect-r1-exact-threshold`)

- R1의 하락 비교에 **R4가 쓰는 `_FLOAT_ABS_TOL` 정본을 그대로** 적용했다.
  🔴 **R1 전용 epsilon을 만들지 않았다** — 같은 판정이 두 값에 살면 하나만 고쳐지는 날
  규칙끼리 갈린다(상수 선언 1개 · 사용처 3곳).
- `round()`·`Decimal` 전환 없음 · threshold·score·saturation 무변경 ·
  R2~R6 의미 무변경 · 프롬프트·API·DB 무접촉.
- 🔴 **초판 S15가 결함을 계약으로 굳혀 놨다** — 「미발화」 사례로 쓴
  `114/120 → 96/120`은 **수학적으로 정확히 15.0pp**인데 float가 `14.999…`로 떨어져
  미발화한 것이었다. 실제로 미달인 **14.5pp**(`200 → 171`)로 바꿨다.
- ⚠ **판정 주 정답률을 50% 이상으로 제한**해야 R1만 잰다 — 그 아래면 R6이 함께 발화해
  **병합 대표가 R6**이 되고 `rule_id`만 보면 *"R1이 안 났다"* 로 읽힌다(실측).

**R3·R6은 같은 감사에서 반례가 발견되지 않았다** — 그래서 손대지 않았다(일괄 변경 금지).

## 6-5. 🔴 드러난 것 — R3의 brief facts가 판정 축과 다른 소스를 읽는다

**B05·B10의 문면이 신호와 어긋난다.**

```
신호      R3 volume_gap (학습 공백)
판정 근거  weekly_activity 2026-07-20 = 0건        ← detection_evidence 정본
응답 evidence  "해당 주 학습 활동 0건"
brief facts   ('이번 주 학습 활동','20건') ('평소 대비','100%')   ← learning_events event_count
결과 문면  "이번 주 학습 활동이 20건으로 나타났고 평소 대비 100%예요"
```

**강사는 `학습 공백` 신호 옆에서 「평소와 같은 수준」이라는 문장을 보게 된다.**

⚠ **LLM 잘못이 아니다.** 받은 `facts`를 그대로 옮겼고 게이트도 통과한다 — `facts` 안의 숫자라
근거 밖 검사에 걸리지 않는다. `briefing_context._r3_facts()`가 `week.event_count`
(=`learning_event` 집계)를 읽는데, R3의 판정은 `student_week_activity` 정본 집계로 한다.

**정확한 축 이름:**

```
R3 판정 정본   detection_evidence.weekly_activity        (백엔드 집계 · 없으면 판정 자체를 안 한다)
브리핑 facts   StudentFeatures.event_count               (learning_event에서 복원한 값)
```

🔴 **픽스처를 맞춰 숨길 문제가 아니다.** 이번 픽스처가 두 축을 어긋나게 준 것은 맞다
(`steady_history()`가 분석 주까지 `solve` 20건을 넣고 `activity_series(counts={0:0})`가 같은 주
집계를 0으로 준다). **그러나 픽스처를 정렬하면 문면만 조용해지고 결함은 그대로 남는다** —
두 축은 **원천이 다른 입력**이라 프로덕션에서도 갈릴 수 있고, 갈리는 날 같은 문장이 나온다.

⇒ **브리핑도 판정 정본을 읽어야 한다.** `_r3_facts()`가 `detection_evidence.weekly_activity`를
읽도록 고치는 것이 해법이다. **이번 회차는 문서 전용이라 고치지 않았다** — 별도 코드 PR이다.
